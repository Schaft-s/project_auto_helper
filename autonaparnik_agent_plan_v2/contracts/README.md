# Контракты версии 2.0

`models.py` — исполняемый эталон контрактов на Pydantic 2.x. Это вспомогательный код спецификации; backend, обучение и сервис в пакете не реализованы. Экспортированные JSON Schema позволяют разработать UI, адаптеры и датасет согласованно.

- `api.schema.json` содержит ChatRequest и AnswerEnvelope в `$defs`; корневой ApiPayloads объединяет пример запроса/ответа для проверки. HTTP POST принимает **только ChatRequest**, а возвращает **только AnswerEnvelope**, без внешней обёртки ApiPayloads.
- `specialist.schema.json` — ровно текстовая структура, генерируемая малой LLM. ModelRun добавляет доверенный backend отдельно.
- `document.schema.json` — запись подготовленного документа, а не формат оригинальной КСО.
- `tool-schemas.json` — две функции приложения для router. Это **не** схемы MCP cyanheads. Реальные MCP-схемы сохраняются после tools/list в T02.

Дополнительные межполевые проверки реализованы model_validator в Python и не полностью выражены JSON Schema: ссылки существуют в текущем ответе, статусы согласованы с содержимым, счётчики не преувеличивают просмотр и executed=true сопровождается метаданными артефакта. Это требует backend-валидации и содержательных тестов; одна схема не гарантирует правильность ремонта или разрешение на публикацию.

При переносе в приложение агенты используют этот файл либо выносят из него общий пакет. Не делать разные SpecialistResult для обучения и serving. При изменении контракта обновить schemas, examples, docs и связанные тесты одним PR. Экспорт и проверка запускаются скриптом `validate_bundle.py` из корня пакета; `--export` пересоздаёт только JSON Schema.

Все examples — искусственные форматные примеры без реальной ремонтной рекомендации. Они не доказывают выполненное обучение или работоспособность модели. Fake hash в fixture не может использоваться в production manifest.
